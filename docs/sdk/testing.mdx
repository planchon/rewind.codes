title: "Testing"
description: "Type-check code, test workflows end to end against a world of rules and handlers in virtual time, keep a workflow's suite green, and fix failed runs with forks."
---

A run's behavior depends only on its code, its input and what the outside world answered. So a workflow is tested by
giving it a world: the answers to its calls, the signals it receives, a start time and a seed. No action is called, and
time is virtual. The complete program of this page is in
[`examples/testing`](https://github.com/planchon/rewind.codes/tree/main/examples/testing).

## Type-check

```ts
const ci = rewind.namespace("ci");
const { ok, diagnostics } = await ci.workflows.check({ actionSet: actionSet.id, code });

for (const d of diagnostics) console.log(`${d.severity} ${d.code} ${d.message}\n${d.frame}`);
```

```text
error TS2322 Type 'number' is not assignable to type 'string'.
7 | export default async function main(input: { repo: string }) {
8 |   const issues = await github.list_issues({ repo: 42, state: "open" });
  |                                             ^^^^
```

Code with only warnings passes. `runs.start` checks the code anyway, unless you pass `check: false`. A check creates
nothing; when the namespace already has the code, it also gives that workflow's id and version.

## Tests

A **test** describes the world a workflow's code meets and what the outside must see at the end. It never names the
code: the code under test is a parameter, so a test written for one version of a workflow runs unchanged against the
next. Tests are always end to end. They check how the run ended and the calls it made, never a variable, a helper or a
log line, so a refactor breaks nothing it should not.

```json closes-once-approved.json
{
  "name": "closes the stale issues once approved",
  "input": { "repo": "acme/api" },
  "world": {
    "actions": {
      "github.list_issues": [
        { "args": { "state": "open" },
          "returns": [{ "number": 4, "updated_at": "2025-10-01T00:00:00Z" }] },
        { "args": { "labels": "reopened" }, "returns": [] }
      ],
      "github.close_issue": { "returns": {} },
      "slack.post_message": { "returns": { "ok": true } }
    }
  },
  "signals": [{ "name": "approval", "payload": { "close": true } }],
  "expect": {
    "status": "completed",
    "output": { "closed": 1, "reopened": 0 },
    "calls": [
      { "action": "slack.post_message", "args": { "channel": "#triage" }, "times": 1 },
      { "action": "github.close_issue", "times": 1 }
    ],
    "order": "listed"
  }
}
```

Run tests against code with `workflows.test`. Each test runs as a **test run**, in its own engine, in virtual time, so a
3-day timeout or a 10-day sleep passes at once; several run at the same time. A test creates and changes nothing: no
workflow, version or test is stored.

```ts
const report = await ci.workflows.test({ actionSet: actionSet.id, code, tests: [closesOnceApproved] });

report.passed; // every test passed
for (const test of report.tests) {
  console.log(test.passed ? "PASS" : "FAIL", test.name, test.problem ?? "");
  for (const failure of test.failures) console.log(`  ${failure}`); // one sentence each, written for a model
}
```

| Field | Meaning |
| --- | --- |
| `name` | Unique within a suite |
| `input` | The run's input; `{}` when absent |
| `start` | When the run starts, in virtual time; `2026-01-01T00:00:00Z` when absent |
| `seed` | The run's seed, 64 lowercase hexadecimal digits; the same fixed seed for every test when absent |
| `world.actions` | For each action, one answer for every call, or a list of rules tried in order (below) |
| `world.handlers` | TypeScript handlers, for answers that compute |
| `world.cassette` | The calls and signals recorded from a run (below) |
| `signals` | Sent to the run, in order. `when` is `"waiting"` (the default: once the run waits for something other than a timer), or a duration of virtual time after the start, such as `"2h"` |
| `expect` | What must hold at the end; what is not given is not checked |
| `from` | For a test [recorded from a run](/sdk/workflows#record-tests-from-runs): the run, the workflow version it ran and its namespace |

A test starts at a fixed time with a fixed seed: its result depends only on the code, the action set, the test and the
[determinism epoch](/concepts/history#determinism-epochs). The same four give the same report, so a test cannot be
flaky.

## The world

**The world is the list of what the code may touch.** A call is answered by the first source that has an answer: the
rules of `world.actions`, then the handlers, then the cassette. A call that no source answers fails with an
`ActionError` (`no recorded response for github.delete_repo({…})`) and fails the test, even if the code catches the
error.

A rule answers the calls whose args contain its `args` (objects compared key by key), or every call when it has none.
It gives `returns`, the result, or `error`, a failure: `{ message, kind?, data? }`, where `kind` is that of a failed
call (`error` when absent). `times` says how many calls it answers; any number when absent.

```json
"world": {
  "actions": {
    "github.list_issues": [
      { "args": { "state": "open" }, "returns": [{ "number": 4 }], "times": 1 },
      { "returns": [] }
    ],
    "slack.post_message": { "error": { "message": "rate limited", "kind": "unavailable", "data": { "retryAfter": 30 } } },
    "workflows.notify.start": { "returns": { "sent": true } }
  }
}
```

A start of a [child run](/sdk/workflows#let-code-start-it) is answered like any call: `returns` is the child's output,
`error` its failure, and no child runs. Each child workflow has its own suite.

Handlers run in an isolate of their own, so they cannot break the code's determinism. The module default-exports its
handlers by full action name or by group; each receives the arguments and
`{ action, runId, seq, delivery, idempotencyKey }`, and returns the result or throws.

```ts Handlers, as world.handlers
const handlers = `export default {
  "github.list_issues": ({ repo }) => [{ number: 4, title: "Crash", repo, updated_at: "2025-01-01T00:00:00Z", labels: [] }],
  slack: {
    post_message: async ({ channel }, call) => ({ ok: true, channel, key: call.idempotencyKey }),
  },
};`;
```

<Warning>
  A run that waits for a signal **with a timeout** can still move by itself in virtual time: the clock goes straight to
  the timeout. Give such a signal a `when` shorter than the timeout, such as `"1h"`; with the default `"waiting"`, it
  would arrive after the timeout fired.
</Warning>

## Expectations

Everything `expect` does not give is not checked.

| Expectation | Holds when |
| --- | --- |
| `status` | The run is in this state: `completed`, `failed`, `cancelled`, `aborted`, or `waiting` for a run that can go no further in virtual time without the outside world (a test of "waits for approval") |
| `output` | The output contains it: objects key by key, recursively; other values equal as JavaScript sees them |
| `error` | The run failed with an error of this `name`, whose message contains `message` |
| `calls` | For each item, the calls to `action` whose args contain `args`: exactly `times` of them, or at least one when `times` is absent. `times: 0` says a call must not happen |
| `order` | `any` (the default), or `listed`: the first call matching each item comes in the order of the items (those with `times: 0` aside) |

Calls the world answers that `calls` does not list are allowed: a fix that adds a harmless read breaks no test. To
forbid a side effect, list it with `times: 0`.

## What a test reports

`workflows.test` answers a test report. Each item of `report.tests`, in the order given:

| Field | What |
| --- | --- |
| `passed` | Every expectation holds |
| `problem` | Why it did not pass: `stale`, `incompatible` or `failed` |
| `failures` | What does not hold, one sentence each, written for a model |
| `status`, `output`, `error`, `abort` | How the run ended; no status for a test that was not run |
| `calls` | How many times each action was called |
| `transcript` | The run's transcript, as `runs.transcript` writes it |

Before a test runs, it is checked against what it runs with, without starting the code. A test that fails a check is
reported with its problem, and is not run:

- **`stale`**: an action of `world.actions` or of `expect.calls` is not in the action set; a rule's `returns` does not
  match the action's output schema, when it declares one; a rule's `args` has a key the action's input schema does not
  declare. An MCP server that changed its tools makes the tests written for the old ones stale.
- **`incompatible`**, for a test of a workflow: the version's input schema refuses the input, or a signal is not one
  the version declares, or its schema refuses the payload. A version that changed its interface makes the tests
  written for the old one incompatible.

A test that runs and does not meet its expectations is **`failed`**.

## Test against a real run

A run's calls and signals, exported as a **cassette**, answer each call with what the real action answered. Export a
cassette from a run that went well, and test the next version of the code against it:

```ts
const cassette = await rewind.runs.export(run.id, { as: "cassette" });

const replayed = await ci.workflows.test({
  actionSet: actionSet.id,
  code: nextVersion,
  tests: [
    {
      name: "does what the run of Monday did",
      input: { repo: "acme/api" },
      world: { cassette }, // its signals are sent when they arrived in the run
      expect: { status: "completed", output: { closed: 2 } },
    },
  ],
});
```

A cassette is matched `sequential` (strict order of the calls) or `by_args` (the action and its args, in any order).
For a workflow, [record tests from its runs](/sdk/workflows#record-tests-from-runs) instead: Rewind picks one run per
path, and keeps the run's start and seed, so `Date.now()` and random values are what they were.

## Workflow suites

A workflow carries a **suite**: the tests every new version must pass. Making a version runs its suite, and a version
is stored only if every test passes. See [Versions and the gate](/sdk/workflows#versions-and-the-gate).

With `workflow`, `workflows.test` runs that workflow's suite too, and checks every test against its version's
interface. The code and the action set default to the version's. This is how a candidate is checked before it becomes
a version:

```ts
// Corrected code, against the suite of the latest version of triage:
await ci.workflows.test({ workflow: "triage", code: corrected, tests: [newTest] });

// The same version on a new action set, whose MCP server changed:
await ci.workflows.test({ workflow: "triage", actionSet: upgraded.id });
```

Tests given alone are not stored. A test joins a workflow's suite only through the gate.

## Fix a failed run

A fork re-executes corrected code against a failed run's history: while it makes the same calls, their recorded
results are reused, then it continues live. In the example, the first version of the code fails on an issue without
labels, after it posted to Slack. The fork does not post again:

```ts
const failed = await ci.runs.start({ actionSet: actionSet.id, code: v1, input, wait: "10s" });
// failed: TypeError: Cannot read properties of undefined (reading 'name')

const fixed = await ci.runs.fork(failed.id, { code: v2, wait: "10s" });
```

```text
v1 01a1e137-7cb0-724e-8ef7-1d0ddee39f8e: failed, TypeError: Cannot read properties of undefined (reading 'name')
fork 01a1e137-7dc2-77bd-8a15-9eac80e24d01: completed { areas: [ 'ci', 'unlabelled' ], closed: 2 }
calls the worker executed, both runs together: [
  'github.list_issues',
  'slack.post_message',
  'github.close_issue #12',
  'github.close_issue #31'
]
```

The fork of a run of a workflow version with a suite runs that suite against the corrected code first. If a test does
not pass, no fork is created: `runs.fork` throws a `tests-failed` error, whose `tests` say which tests failed and why.
A fix that breaks another behavior never reaches production calls.

```ts
try {
  await ci.runs.fork(failed.id, { code: v2 });
} catch (error) {
  if (!isProblem(error, "tests-failed")) throw error;
  for (const test of error.tests.filter((t) => !t.passed)) console.log(test.name, test.failures);
}
```

## In CI, without a server

The `rewind` CLI runs tests in its own process, without a server. A tests file is a JSON array of tests; their
`world.handlers` and `world.cassette` may name files, relative to the tests file:

```json triage.tests.json
[
  {
    "name": "closes the stale issues once approved",
    "input": { "repo": "acme/api" },
    "world": { "handlers": "triage.handlers.ts", "actions": { "github.close_issue": { "returns": {} } } },
    "signals": [{ "name": "approval", "payload": { "close": true } }],
    "expect": { "status": "completed", "output": { "closed": 1 } }
  },
  {
    "name": "does what the run of Monday did",
    "input": { "repo": "acme/api" },
    "world": { "cassette": "cassettes/monday.json" },
    "expect": { "status": "completed", "output": { "closed": 2 } }
  }
]
```

```bash
rewind test triage.ts                                           # the tests of triage.tests.json, next to the code
rewind test triage.ts --tests ci.tests.json --action-set action-set.json
rewind test triage.ts --workflow triage                         # and the suite of the workflow, on the server
rewind test --workflow triage --action-set action-set.json      # the version's own code, on a new action set
rewind replay run.json                                          # re-executes an exported run and checks determinism
rewind replay run.json --code v2.ts                             # is v2 compatible with that history? where does it diverge?
```

`rewind test` answers a call with the test's rules, its handlers, its cassette, then the static responses of
`rewind.actions.json`, last. Without an action set, the action set is the actions the tests answer, as harness actions.
It exits with 0 when every test passes, and 1 otherwise. See [the CLI](/sdk/cli).
