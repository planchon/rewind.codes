title: "Host tools"
description: "Functions of your harness that scripts call: the worker that executes them, their failures, retries and answers that take days."
---

A host tool is a function of your harness that scripts call like any tool: ask the end user, call another model, start
a sub-agent, read your database. Declare it in the [toolset](/sdk/toolsets), then run a **worker** that executes it.

The worker holds a **task stream** open to Rewind and is handed each call to its tools as it becomes ready. It runs
your handler and answers with the result, like a Temporal activity worker. It runs in your infrastructure; Rewind
never connects to it: the stream is a request the worker makes.

```ts
import { HostToolError, Rewind } from "@rewind.codes/sdk";

const rewind = new Rewind();

const worker = rewind.worker({
  toolset: toolset.id,
  concurrency: 10,
  tools: {
    "crm.find_customer": async ({ email }: { email: string }, ctx) => {
      // ctx.namespace is the end user the run acts for: act on their data only.
      const customer = await crm.find(ctx.namespace, email, { signal: ctx.signal });
      if (!customer) throw new HostToolError(`no customer ${email}`, { data: { code: "not_found" } });
      return customer;
    },
  },
});

process.on("SIGTERM", () => worker.stop()); // takes no new call, and waits for the handlers in flight to answer
```

## The handler's context

| Field | What |
| --- | --- |
| `ctx.namespace` | The end user the run acts for. One worker with your key serves every end user |
| `ctx.idempotencyKey` | `{run_id}/{seq}`, the same on every attempt of this call. Give it to the APIs you call, so a call made again does not repeat its effect |
| `ctx.attempt` | From 1. Above 1, an earlier attempt was interrupted: the call may already have happened |
| `ctx.runId`, `ctx.seq` | The run, and the call's position in it |
| `ctx.labels` | The run's labels |
| `ctx.signal` | Aborted when the call stops waiting for its answer: its run ended, or its call timed out. The result is then dropped |
| `ctx.traceparent` | The W3C trace context, with the tool call's span as parent |
| `ctx.defer()` | Answer later, by a token (below) |

## Failures

- A thrown **`HostToolError`** is the tool's failure: the script gets a `ToolError` with its `message` and `data`, and
  decides what to do. With `retryable: true`, a tool under the `retry` policy is called again later.
- **Any other exception** fails the call too, with `Name: message`, and is reported to `onError`.

```ts In the script
import { ToolError } from "rewind";

try {
  const customer = await crm.find_customer({ email });
} catch (error) {
  if (error instanceof ToolError && (error.data as { code?: string })?.code === "not_found") {
    // create it instead
  } else throw error;
}
```

A worker that dies mid-call closes its stream. Its calls wait for it to come back for the tool's grace (60 seconds by
default, [below](#the-task-stream)); after it, under the `retry` policy, each call is handed to another worker with the
same idempotency key, up to 5 attempts. Under `at_most_once`, it fails with `outcomeUnknown: true`: declare it for a
tool that must never run twice, such as asking the user a question.

## Answers that take days

A handler can defer its answer: the call becomes `deferred`, its slot on the stream is free, and it is answered later
by its token, from any process, whether the worker's stream stays open or not. The run waits durably meanwhile.

```ts
const worker = rewind.worker({
  toolset: toolset.id,
  tools: {
    ask_user: async ({ question }: { question: string }, ctx) => {
      const later = await ctx.defer({ timeout: "3d" }); // bounded by the run's TTL
      await inbox.save({ user: ctx.namespace, question, token: later.token });
      // The return value is not an answer: whoever holds the token answers.
    },
  },
});

// Later, maybe in another process, when the user answers:
await rewind.tasks.complete(token, { answer: "yes" });
// Or: await rewind.tasks.fail(token, { message: "the user is away" });
```

The complete program is in [`examples/host-tools`](https://github.com/planchon/rewind.codes/tree/main/examples/host-tools).

## The task stream

The worker opens one stream, `GET /v1/tasks/stream`, with its tools, its toolset, its `slots` (its `concurrency`) and
its `worker` id, drawn once when it starts (`worker.id`). The server sends a `task` event for each call as it becomes
ready, with the call's token, up to `slots` in flight on the stream at once; and a `gone` event when a call handed on it
stops waiting for its answer (its run ended, its call timed out), which aborts the handler's `ctx.signal`. Nothing is
sent while a handler runs: the open stream is what keeps its calls alive.

- **After a drop**, the worker opens the stream again with the same id, after a backoff (500 ms, doubled up to 30 s),
  and its handlers go on. A stream opened again with the same `worker` within the grace keeps the calls handed on the
  one that closed: they are not handed again. A stream silent for 45 seconds is taken as broken and opened again: the
  server writes a comment at least every 15 seconds.
- **The grace** is how long a call handed on a closed stream waits for its worker to come back: the tool's
  `heartbeatTimeout` in its [policy](/sdk/toolsets#policies), 60 seconds by default. After it, the call is interrupted:
  handed to another worker with `ctx.attempt` + 1 under `retry`, failed with `outcomeUnknown` under `at_most_once`.
- **`stop()`** keeps the stream open with no slot while the handlers in flight answer: no new call is handed to the
  worker, and the calls it holds stay alive.

Any language can hold the stream without the SDK: it is server-sent events, `task` (the task, with its `token`) and
`gone` (`{ token }`), each answered with `POST /v1/tasks/{token}/complete`, `/fail` or `/defer`. `rewind.tasks.stream`
reads one stream at the level of the API.

## Options

| Option | Default | What |
| --- | --- | --- |
| `tools` | | The handlers, by tool name as the toolset declares it (`"crm.find_customer"`). The worker is handed only these tools |
| `toolset` | | Only the calls of runs of this toolset. Leave it out to serve every toolset that declares these tools |
| `concurrency` | 10 | Handlers running at once: the slots of its stream, 100 at most |
| `signal` | | Stops the worker when aborted, as `stop()` |
| `onError` | `console.error` | Called with what fails along the way, and where: the `stream`, an `answer`, a `handler` |
| `timings` | | The backoff after a drop (`backoffMs`, 500; `maxBackoffMs`, 30 000) and the silence after which a stream is taken as broken (`silenceMs`, 45 000) |

A refused request (a key refused with 401 or 403, an unknown toolset) stops the worker: `worker.done` rejects. Other
failures are reported to `onError`, and the stream is opened again. A worker holding an end user's token, instead of a
key, is handed only the calls of that end user's runs.

## One worker per environment

A worker is handed the calls of the runs its key sees. With a key limited to labels, those are the runs carrying them:
give each environment of your organization a key limited to its label, with the role `harness` or `worker`, and its
worker answers only its own runs' calls, against its own database, even when every environment registers the same
toolset.

```ts
// REWIND_API_KEY is limited to { env: "dev" } on the dev server, to { env: "prod" } in production.
const rewind = new Rewind();

// Runs this key starts carry env=dev; this worker never receives a call of an env=prod run.
const worker = rewind.worker({
  toolset: toolset.id,
  tools: { "db.find_order": async ({ id }: { id: string }) => db.orders.find(id) },
});
```

The run's labels are in `ctx.labels`. A token of another environment's call is answered as a call that no longer
exists (410).
