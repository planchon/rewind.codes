---
title: "Secrets"
description: "Named values a run attaches at start, server by server: the organization's and each end user's own. Written, never read back; read only by Rewind's dispatcher."
---

A **secret** is a named value, encrypted at rest, that only Rewind's dispatcher reads, for the runs that attached it:
a GitHub token, a Zendesk API key. The server's `auth` in the [toolset](/sdk/toolsets#how-calls-prove-who-calls) says
where it goes (a header, an environment variable); the run says which secret it reads.

| | The organization's | An end user's |
| --- | --- | --- |
| Belongs to | Your organization, shared by every end user | One [namespace](/sdk/end-users): Alice's GitHub token |
| Attached as | `org/<name>` | `ns/<name>`: the secret `<name>` of the run's own namespace |
| Labels | Its own: a key limited to `env=prod` sees and attaches only the secrets labelled `env=prod` | None: the namespace is its scope |
| Written with | `rewind.secrets.put(name, { value, labels })` | `rewind.namespaces.secrets.put(namespace, name, { value })` |

A name is 1 to 64 lowercase letters, digits, `-` and `_`, starting with a letter; a value is a string of at most 16 KiB.

## Write a secret

```ts
// The organization's: every end user's runs may attach it.
await rewind.secrets.put("zendesk", { value: process.env.ZENDESK_TOKEN!, labels: { env: "prod" } });

// An end user's own, when they connect their GitHub account.
await rewind.namespaces.secrets.put(user.id, "github", { value: githubTokenOf(user) });
```

Secrets are **write-only**: no answer of the API holds a value, not even to whoever wrote it. They are listed with
their metadata: their labels, who wrote them and when, their reads per day over 30 days, their last read (run,
namespace, date; `run` and `namespace` are `null` when a toolset's registration read it to list a server's tools).

```ts
const secrets = await rewind.secrets.list(); // [{ name, reference: "org/zendesk", labels, updatedBy, reads, lastRead, … }]
const alices = await rewind.namespaces.secrets.list(user.id);
```

Secrets never enter the sandbox, the journal, a cassette, a trace, nor an answer of the API. The script never sees
them: it calls `github.list_issues(…)`, and the dispatcher adds the token to the request.

## Attach secrets to a run

A run reads only the secrets it attaches at start, server by server, in the request that gives the script, never in
the script:

```ts
const run = await rewind.namespace(user.id).runs.start({
  toolset: toolset.id,
  script,
  secrets: { github: "ns/github", zendesk: "org/zendesk" },
});
run.secrets; // { github: "ns/github", zendesk: "org/zendesk" }: names, never values
```

| Where | The attachments |
| --- | --- |
| `runs.start` with a script | The request's `secrets` |
| `runs.start` with a `workflow`, and `triage.start(…)` in a script | The version's, saved with it: the request gives none |
| `runs.fork` | The parent's, unless the request gives its own `secrets` |
| `toolsets.create` | Organization's secrets only, to list the tools of an MCP server that needs one; no run keeps them |

Nothing falls back on another secret: Alice's run that attaches `ns/github` never calls with the organization's token,
nor with Bob's.

**Who may attach.** A namespace's secret: whoever starts a run in that namespace, since it is the end user's own. An
organization's secret: whoever holds `secrets:use`, for a secret whose labels are within their grant's; an end user's
token only if it was given `secrets:use`.

**A workflow version is the permission.** Saving a version checks its attachments against the saver: an organization's
secret must exist and be theirs to attach; an `ns/` secret has no namespace yet, so only its name is checked. A run of
the version then needs no right on its secrets, only its `ns/` secrets to exist in the run's namespace.

```ts
await rewind.workflows.create({ name: "triage", script, toolset: toolset.id, input, output, secrets: { github: "ns/github" } });
```

## When an attachment is refused

The start is refused before any run exists, with `secret-required` (422), when the script imports a server whose
`auth` takes a secret and nothing is attached for it, when an attachment names a server that takes none or a secret
that does not exist, or when the caller may not attach it. `error.attachments` says which, and what may be attached
instead:

```ts
import { isProblem } from "@rewind.codes/sdk";

try {
  await rewind.namespace(user.id).runs.start({ toolset: toolset.id, script });
} catch (error) {
  if (isProblem(error, "secret-required")) {
    for (const a of error.attachments) {
      console.log(a.server, a.problem, a.attachable); // "github" "missing" ["ns/github", "org/github"]
    }
  }
}
```

| `problem` | Means |
| --- | --- |
| `missing` | The script imports the server, whose `auth` takes a secret, and nothing is attached for it |
| `takes_none` | The server's `auth` takes no secret |
| `unknown` | No such secret: an `ns/` secret is looked up in the run's namespace |
| `forbidden` | The caller may not attach it: no `secrets:use`, or labels outside its grant |

The agent tools tell the model the same, so it attaches what `attachable` lists and tries again.

## When a server refuses a secret

A token can expire during a ten-day sleep. When the server answers 401, or the secret the run attached was deleted, the
call is **parked**, and your harness gets the webhook [`credentials.expired`](/sdk/webhooks), with its `reason`
(`refused` or `missing`) and the `secret` the run attached. Put the secret again under the same name: the parked calls
of every run that attaches it are sent again, with the same idempotency key.

```ts
await rewind.namespaces.secrets.put(user.id, "github", { value: await refreshGithubToken(user) });
```

## Before deleting a secret

`usage` says what reads a secret, and what deleting it would stop: the active runs that attach it, those of them
waiting on a call it serves, and the workflows whose latest version attaches it.

```ts
const usage = await rewind.secrets.usage("zendesk");
// { activeTotal: 12, waitingTotal: 1, workflows: [{ name: "support", version, servers: ["zendesk"] }], … }
await rewind.secrets.delete("zendesk"); // their next call to zendesk is parked
```

The dashboard's [Secrets](/dashboard/secrets) view shows the same before it deletes one.

## Permissions

| Permission | Allows |
| --- | --- |
| `secrets:read` | Listing the secrets and their usage, never a value; reading the signing keys' ids |
| `secrets:write` | Putting and deleting secrets |
| `secrets:use` | Attaching an organization's secret to a run or a workflow |

A key or a grant limited to labels sees, writes and attaches only the organization's secrets carrying all its labels,
and the secrets it writes take them. It reads and attaches a namespace's secrets as any key does, and never writes one:
a namespace's secret serves the end user's runs whatever their labels. An end user's token with `secrets:write` writes
its own namespace's secrets.
