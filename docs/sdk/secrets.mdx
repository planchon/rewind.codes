---
title: "Secrets"
description: "Named values a run uses, named server by server at its start: the organization's and each end user's own. Written, never read back; read only by Rewind's dispatcher."
---

A **secret** is a named value, encrypted at rest, that only Rewind's dispatcher reads, for the runs that use it: a
GitHub token, a Zendesk API key. The server's `auth` in the [action set](/sdk/action-sets#how-calls-prove-who-calls)
says where it goes (a header, an environment variable); the run says which secret it uses.

| | The organization's | An end user's |
| --- | --- | --- |
| Belongs to | Your organization, shared by every end user | One [namespace](/sdk/end-users): Alice's GitHub token |
| Named by a run as | `org/<name>` | `ns/<name>`: the secret `<name>` of the run's own namespace |
| Labels | Its own: a key limited to `env=prod` sees and uses only the secrets labelled `env=prod` | None: the namespace is its scope |
| Written with | `rewind.secrets.put(name, { value, labels })` | `rewind.namespaces.secrets.put(namespace, name, { value })` |

A name is 1 to 64 lowercase letters, digits, `-` and `_`, starting with a letter; a value is a string of at most 16 KiB.

## Write a secret

```ts
// The organization's: every end user's runs may use it.
await rewind.secrets.put("zendesk", { value: process.env.ZENDESK_TOKEN!, labels: { env: "prod" } });

// An end user's own, when they connect their GitHub account.
await rewind.namespaces.secrets.put(user.id, "github", { value: githubTokenOf(user) });
```

Secrets are **write-only**: no answer of the API holds a value, not even to whoever wrote it. They are listed with
their metadata: their labels, who wrote them and when, their reads per day over 30 days, their last read (run,
namespace, date; `run` and `namespace` are `null` when an action set's registration read it to list a server's tools).

```ts
const secrets = await rewind.secrets.list(); // [{ name, reference: "org/zendesk", labels, updatedBy, reads, lastRead, … }]
const alices = await rewind.namespaces.secrets.list(user.id);
```

Secrets never enter the sandbox, the history, a cassette, a trace, nor an answer of the API. The workflow never sees
them: it calls `github.list_issues(…)`, and the dispatcher adds the token to the request.

## The secrets a run uses

A run reads only the secrets its start names, server by server, in the request that gives the code, never in the code:

```ts
const run = await rewind.namespace(user.id).runs.start({
  actionSet: actionSet.id,
  code,
  secrets: { github: "ns/github", zendesk: "org/zendesk" },
});
run.secrets; // { github: "ns/github", zendesk: "org/zendesk" }: names, never values
```

| Where | The secrets used |
| --- | --- |
| `runs.start` with code | The request's `secrets` |
| `runs.start` with a `workflow`, and `triage.start(…)` in a workflow's code | The version's, given when the version was made: the request gives none |
| `runs.fork` | The source's, unless the request gives its own `secrets` |
| `actionSets.create` | Organization's secrets only, to list the tools of an MCP server that needs one; no run keeps them |

Nothing falls back on another secret: Alice's run that uses `ns/github` never calls with the organization's token, nor
with Bob's.

**Who may use them.** A namespace's secret: whoever starts a run in that namespace, since it is the end user's own. An
organization's secret: whoever holds `secrets:use`, for a secret whose labels are within their grant's; an end user's
token only if it was given `secrets:use`.

**A workflow version is the permission.** Making a version checks the secrets it names against whoever makes it: an
organization's secret must exist and be theirs to use; an `ns/` secret has no namespace yet, so only its name is
checked. A run of the version then needs no right on its secrets, only its `ns/` secrets to exist in the run's
namespace.

```ts
await rewind.workflows.create({ name: "triage", code, actionSet: actionSet.id, input, output, secrets: { github: "ns/github" } });
```

## When a secret is refused

The start is refused before any run exists, with `secret-required` (422), when the code imports a server whose `auth`
takes a secret and none is named for it, when the start names a secret for a server that takes none or a secret that
does not exist, or when the caller may not use it. `error.secrets` says which server is at fault, why, and which
secrets the caller may use for it instead:

```ts
import { isProblem } from "@rewind.codes/sdk";

try {
  await rewind.namespace(user.id).runs.start({ actionSet: actionSet.id, code });
} catch (error) {
  if (isProblem(error, "secret-required")) {
    for (const problem of error.secrets) {
      console.log(problem.server, problem.problem); // "github" "missing"
    }
  }
}
```

| `problem` | Means |
| --- | --- |
| `missing` | The code imports the server, whose `auth` takes a secret, and none is named for it |
| `takes_none` | The server's `auth` takes no secret |
| `unknown` | No such secret: an `ns/` secret is looked up in the run's namespace |
| `forbidden` | The caller may not use it: no `secrets:use`, or labels outside its grant |

The agent tools tell the model the same, so it names a secret it may use and tries again.

## When a server refuses a secret

A token can expire during a ten-day sleep. When the server answers 401, or the secret the run uses was deleted, the
call is **parked**, and your harness gets the webhook [`secret.expired`](/sdk/webhooks), with its `reason` (`refused`
or `missing`) and the `secret` the run uses. Put the secret again under the same name: the parked calls of every run
that uses it are delivered again, with the same idempotency key.

```ts
await rewind.namespaces.secrets.put(user.id, "github", { value: await refreshGithubToken(user) });
```

## Before deleting a secret

`usage` says what reads a secret, and what deleting it would stop: the active runs that use it, those of them waiting
on a call it serves, and the workflows whose latest version uses it.

```ts
const usage = await rewind.secrets.usage("zendesk");
// { activeTotal: 12, waitingTotal: 1, workflows: [{ name: "support", version: 4, servers: ["zendesk"] }], … }
await rewind.secrets.delete("zendesk"); // their next call to zendesk is parked
```

The dashboard's [Secrets](/dashboard/secrets) view shows the same before it deletes one.

## Permissions

| Permission | Allows |
| --- | --- |
| `secrets:read` | Listing the secrets and their usage, never a value; reading the signing keys' ids |
| `secrets:write` | Putting and deleting secrets |
| `secrets:use` | Naming an organization's secret for a run or a workflow version to use |

A key or a grant limited to labels sees, writes and uses only the organization's secrets carrying all its labels, and
the secrets it writes take them. It reads and uses a namespace's secrets as any key does, and never writes one: a
namespace's secret serves the end user's runs whatever their labels. An end user's token with `secrets:write` writes
its own namespace's secrets.
