title: "Secrets"
description: "Your organization's secrets and each end user's: who wrote them, how often they are read, what attaches them. A value is written, never shown."
---

The Secrets view lists your organization's [secrets](/sdk/secrets), the values the runs attach as `org/<name>`. Each end
user's own secrets (`ns/<name>`) are on their [namespace's page](/dashboard/namespaces#one-end-user), in the same table.
It needs `secrets:read`; writing and deleting need `secrets:write`.

| Column | Shows |
| --- | --- |
| **Name** | The name, and how a run attaches it: `org/zendesk` |
| **Labels** | An organization's secret's labels: a key or a member limited to `env:prod` sees and attaches only the secrets carrying it |
| **Written** | Who wrote it last (a member, a key, an end user's token) and when; hover for who created it |
| **Reads, 30 days** | Its reads per day, and how many in all |
| **Last read** | When, by which run (it opens the run), and for an organization's secret, in which namespace; or *at a toolset's registration*, which reads an organization's secret to list the tools of the server it is attached for |
| **Attached by** | What reads it now: the active runs that attach it (hover for the list, those waiting on a call it serves marked), and the workflows whose latest version attaches it, each opening in [Testing](/dashboard/testing) |

## Write a secret

**New secret** asks, in a dialog, for a name (lowercase letters, digits, `-` and `_`), the value and, for an
organization's secret, its labels. The value is typed in a password field, sent once and never shown again: no page
and no answer of the API reads it back, not even to whoever wrote it. A member limited to labels writes secrets that
carry them.

**New value** on a row replaces the value and keeps the labels. The calls parked because the secret was missing or
refused, in the runs that attach it, are sent again with the same idempotency key.

## Delete a secret

**Delete…** first reads what the secret serves, and says in the dialog what deleting it would stop:

- the active runs that attach it: their next call to the server it serves is parked, until a secret of the same name
  is put again;
- those of them waiting on such a call now;
- the workflows whose latest version attaches it, with the servers it serves there: for an end user's secret, their
  runs in that namespace are refused at start.

Then **Delete**, in red, deletes it. A deleted secret cannot be restored.

## Who sees what

| Permission | In this view |
| --- | --- |
| `secrets:read` | The view, the secrets' metadata and what attaches them; never a value |
| `secrets:write` | **New secret**, **New value**, **Delete…** |

A member or a key limited to labels sees only the organization's secrets carrying all of them, and never writes an end
user's. The run's page names the secrets each run attached, by server, in its details.
