Open a run from anywhere: a row of Runs, a figure of the Overview, Find with its handle or its id. A run is named by its
**handle**, `namespace/origin/suffix`: for whom it ran, what ran (its workflow's name, else its workflow's short id),
and a suffix that tells it apart, as in `dana/triage/06bqx3k9f2mt`. A handle never changes: a run started before
workflows had ids keeps the origin it was given then, its code's title as a slug, or `script`. Its page is at that path, and the API takes the
handle wherever it takes a run. Its header shows its handle, a **Test run** or quarantine tag when it has one, and its
**Controls**; its sidebar, its sections and its details: namespace, workflow and version (`triage v12`), the run that
started it, code, action set, calls, its id, trace id, labels and the secrets it uses. A run that is still going
updates live, step by step.

## Controls

The header holds the run's **Forks**, and beside them a **Controls** menu with what your role allows:

- **Send a signal**, with `runs:control`, while the run has not ended. When the run waits for a signal, **Send approval**
  (the signal's name) opens a form with a JSON editor for its payload; **Send a signal** sends any name, which the run
  receives when it waits for it. For a run of a version that declares its signals, the form lists them, with each
  payload filled in from its schema. If the server refuses the payload, its reason shows under the editor. A signal
  arrives once, even if you send the form again after a network error. **Signal sent** shows beside the menu until
  the run receives it.
- **Cancel run**, with `runs:control`, asks you to confirm, then **Cancelling…** shows beside the menu until the run
  ends.
- **Export run** downloads the run export, which replays on its own (`rewind replay run.json`); **Export cassette**
  downloads its calls and signals, for [tests](/sdk/testing#test-against-a-real-run).

## Debugger

The debugger is the run's code, across the page, with what each line caused beside it: calls with their duration, log
lines, timers, signal waits. Above it, the **timeline** shows each call, timer and signal wait as a span, with idle
time compressed. Under it, the **step** and what you selected: a line, a note beside it, a span of the timeline. When
the run waits, a banner says for what, at which line, and how to answer.

### The time cursor

A run's history is a sequence of **steps**: something from outside (the start, a call's result, a timer, a signal, a
cancellation) and what the code did in response. The cursor steps through them like a debugger:

- **Step back**, **Step**, first and last, or the <kbd>←</kbd> and <kbd>→</kbd> keys. **every step** also stops on the
  steps that change nothing in the code.
- At each step, the code marks the awaits that just resumed, the calls issued, those still open and those done. The
  panel under the code says why the run woke up, what it did, and where it is paused.
- **Hover** an underlined call to see its arguments and result as known at that step, or a variable bound to an awaited
  call (`const issues = await github.list_issues(…)`), or `input`, to see its value. **Click** to pin it as a watch.
- The step is in the URL (`?step=`): a link opens the run at that moment. On a live run, the cursor follows the head.

<Note>
  Only values that crossed the history are known: inputs, results, signals, and the variables bound to an awaited call.
  What the code computes in between is not recorded, and the dashboard runs no code.
</Note>

Payloads show their size, digest and preview; their full value loads on demand, as a tree whose objects and arrays
fold. The arrows at the right of a payload open it large, to read a long input or result at the width of the screen.

## History

Every event of the run, at `/runs/<handle>/history`: its index, its time from the start, the event, its detail and its
line. Select one to see it in full.

## Logs

The code's `console.*` lines, with their level and line.

## Runs started

The child runs this run started from [`rewind:workflows`](/concepts/workflows#started-by-code), each with how it ended,
the call that started it, and whether it is detached. `triage.start(…)` and `run.signal("approval", …)` read as the code
wrote them.
