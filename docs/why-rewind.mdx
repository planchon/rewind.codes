## The problem with one tool call at a time

In a classic agent loop, every tool call is a round trip through the model. To close the stale issues of a repository,
the model lists the issues, reads all of them in its context, decides, then calls `close_issue` once per issue, each
call a new turn. That has costs that grow with the task:

- **Tokens and latency.** Every intermediate result goes through the context, and every step waits for a model call.
- **Loops and parallelism in prose.** "For each of these 40 issues" is expressed in tokens, not in a `for` loop.
- **Tasks longer than a request.** "Wait for a manager's approval, then refund" does not fit in one HTTP request, and
  rarely in one conversation turn.
- **No record.** When a call fails halfway, nobody can say exactly what happened, replay it, or fix it without
  repeating the side effects.

## What Rewind changes

<Steps>
  <Step title="The model writes the whole procedure">
    One workflow calls every action the task needs, with loops, `Promise.all`, filters and error handling written in
    TypeScript. Only its output goes back into the context, bounded to 256 KiB, with a call that reads the rest.
  </Step>
  <Step title="Rewind checks it before it runs">
    Your actions are compiled into TypeScript declarations. The code is type-checked against them in strict mode, so
    `github.list_issues({ repo: 42 })` is refused with a diagnostic written for the model, before any run exists.
  </Step>
  <Step title="The run is durable">
    A workflow can `await sleep("10d")` or wait for a signal for days. Nothing holds it in memory meanwhile: when what
    it waits for arrives, Rewind rebuilds the run from its history and continues. Crashes and deploys are harmless.
  </Step>
  <Step title="Every run can be replayed, tested and debugged">
    The history is enough to re-execute a run locally, to turn it into a test, to step through it in the dashboard, or
    to fork it with corrected code that does not repeat the calls already made.
  </Step>
</Steps>

## Deterministic by construction

Replaying a run only works if the code computes the same thing every time. Workflow engines ask developers to keep
their code deterministic, and to version it when it changes. Rewind owns the runtime, so it guarantees determinism
itself:

- `Date.now()`, `new Date()` and `performance.now()` return **logical time**, which only moves when the outside world
  speaks, identically on replay.
- `Math.random()` and `crypto.randomUUID()` are seeded per run.
- There is no file system, no network outside your actions, no environment, nothing that could differ between two
  executions.
- Code is immutable and content-addressed: a run always replays the exact code it started with, and a new version of
  its workflow never changes it.

What still changes is Rewind itself, and a [determinism epoch](/concepts/history#determinism-epochs) versions it.

## Built for products with many users

- **Namespaces.** Each end user of your product has one: their runs, workflows, secrets and use, invisible to everyone
  else. An agent acting for one end user holds a token of their namespace only.
- **Quotas.** Active runs, runs and CPU per month, distinct workflows, the longest TTL and the longest code, per end
  user, so one end user cannot exhaust your platform.
- **Permission gates.** An action with the `approval` policy waits for your harness before each call. Workflows never
  see a secret: a run names the secrets it uses at start, and only the dispatcher reads them.
- **Calls your backend can trust.** Rewind signs each call to your own APIs with your organization's key, naming the
  end user: your backend checks it with [`verifyRewindCall`](/sdk/signed-calls), and Rewind keeps no secret of yours.

## How it compares

|  | Tools through the conversation | A code sandbox | A workflow engine | Rewind |
| --- | --- | --- | --- | --- |
| Who writes the procedure | The model, one call per turn | The model | Your engineers, deployed ahead of time | The model |
| Calls your MCP servers, APIs and functions | Yes | You wire them in | Through activities you write | Yes: typed `rewind:actions` |
| Checked before it runs | Schema per call | Rarely | At build time | Type-checked against your actions |
| Waits days, survives restarts | No | No | Yes | Yes |
| Determinism | Not applicable | Not guaranteed | By developer discipline | By construction |
| Replay, recorded tests, forks | No | No | Replay | Yes |
| Isolation per end user | Yours to build | Yours to build | Yours to build | Namespaces, tokens, quotas |

## When Rewind is not the right tool

- A single tool call answers the task: calling the tool directly is simpler.
- The code needs a file system, a shell or npm packages. A workflow imports only `rewind`, `rewind:actions` and
  `rewind:workflows`. Give it an action that does the work instead: a harness action runs anywhere you want.
- Heavy computation. Each call into a workflow's code has a CPU budget (5 seconds by default), and its heap is bounded
  (128 MiB by default). Workflows orchestrate; actions compute.
